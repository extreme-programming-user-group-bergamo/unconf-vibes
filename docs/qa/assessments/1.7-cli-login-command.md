## Findings

### Major (1) — RESOLVED

#### M1: HTTP Client not injected via constructor — partially violates DI standard

**Files:** `internal/cli/login.go:49-53`, `internal/cli/logout.go:38-43`

**Description:**
The `AuthClient` interface (`login.go:18-21`) and `RevokeClient` interface (`logout.go:16-18`) are defined but never used for constructor injection. Both `runLogin` and `runLogout` construct the API client internally via `config.LoadConfig()` + `client.NewClient()`:

```go
// login.go:49-53 — client created internally, not injected
cfg, err := config.LoadConfig(ctx, config.LoadOptions{})
...
apiClient := client.NewClient(cfg.GetAPIEndpoint())
```

This means:
- Tests must use `t.Setenv("UNCONF_API_ENDPOINT", srv.URL)` + `httptest.Server` instead of injecting a mock
- The `AuthClient` interface is only used in `pollForToken()` signature, not in command construction
- Violates the "constructor injection, no globals" coding standard (Rule 6)

**Impact:** Tests work but are tightly coupled to environment variables. Future changes to config loading affect login/logout tests. Pure DI would improve isolation.

**Recommendation:** Inject `AuthClient`/`RevokeClient` into `newLoginCmd`/`newLogoutCmd` alongside `TokenStore`. The interfaces are already defined — wire them through. Alternatively, accept a factory/provider. This can be done in a follow-up without blocking merge.

### Minor (4) — m1, m2 RESOLVED; m3, m4 deferred

#### m1: Dead code in context cancellation test

**File:** `internal/cli/login_test.go:224-226`

```go
go func() {
    <-make(chan struct{}) // We won't wait — cancel immediately to test
}()
```

This goroutine blocks forever on an unbuffered channel and leaks. The cancel is called afterwards so the test still exercises the pre-cancelled context path, but the goroutine is never cleaned up during the test. Either remove the goroutine entirely or use a proper `t.Cleanup`-based cancellation pattern.

#### m2: No test for `SaveTokens` error path in login flow

**File:** `internal/cli/login_test.go`

There is no test case where `tokenStore.SaveTokens()` returns an error (e.g., keyring write failure). The `login.go:72-74` error path (`"failed to save authentication tokens"`) is untested.

**Recommendation:** Add a test using `auth.NewMockTokenStoreWithError(err)` where the store is pre-loaded with no valid token but errors on `SaveTokens`.

#### m3: No table-driven tests for command tests

**Files:** `internal/cli/login_test.go`, `internal/cli/logout_test.go`

The coding standards recommend table-driven tests for variations. The login and logout tests are written as individual functions. While this works and each test is clear, the pattern is inconsistent with the project standard.

**Recommendation:** Consider refactoring into table-driven format in a future pass, particularly for the login error scenarios (server error, access denied, expired code) which share significant setup.

#### m4: Client `ExchangeDeviceCode` double-parses 202 response body

**File:** `internal/client/client.go:119-131`

Resty's `SetResult(&tokenResp)` auto-parses on 2xx (including 202), populating an empty `TokenResponse`. The code then manually `json.Unmarshal(resp.Body(), &pending)` to re-parse. This works correctly but is redundant — the body is parsed twice.

**Recommendation:** For the `ExchangeDeviceCode` method, avoid `SetResult` and do manual parsing for all status codes, or check `resp.StatusCode() == 200` before using the auto-parsed result.

---

### Suggestions (3)

#### S1: Consider adding a `--timeout` flag to login

The current implementation uses `expires_in` from the device flow response (typically 900s). A user-configurable timeout may be useful for CI environments or testing.

#### S2: Log with structured fields consistently

`login.go` logs `slog.Info("login: starting device flow", "api_endpoint", ...)` mixing prefix in the message with structured fields. Consider using a consistent approach: either structured-only fields or a logger with a preset group.

#### S3: `RevokeClient` interface is redundant with `AuthClient`

`logout.go` defines a separate `RevokeClient` interface with only `RevokeToken`. If DI is adopted (per M1), consider unifying into a single `AuthClient` interface covering all auth methods, or use a broader `APIClient` interface.
