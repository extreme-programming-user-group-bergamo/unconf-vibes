**Status:** Done

**Issue Type:** Story

## Story

**As a** developer,  
**I want** the roommate request data model and API endpoints,  
**so that** users can request and manage roommates.

---

## Acceptance Criteria

1. `roommate_requests` table: id, requester_id, target_id, room_id, status (pending/accepted/declined), created_at
2. `POST /requests` creates a roommate request
3. `GET /requests` returns user's incoming and outgoing requests
4. `PUT /requests/{id}/accept` accepts request
5. `PUT /requests/{id}/decline` declines request
6. When accepted, target user added to requester's room booking
7. Validation: can't request if room is full, can't request self

### Data Models

- Architecture defines `RoommateRequest` with `id`, `requester_id`, `target_id`, `room_id`, `status`, `created_at`, and optional `responded_at`.
- `RoommateRequest` relates to `User` (sender/receiver) and `Room`.
- Booking model remains the source of room occupancy state used during accept flow updates.
- [Source: docs/architecture/4-data-models.md#41-entity-relationship-overview]
- [Source: docs/architecture/4-data-models.md#46-roommaterequest]
- [Source: docs/architecture/4-data-models.md#45-booking]

### API Specifications

- Request endpoints are explicitly defined: `POST /requests`, `GET /requests`, `PUT /requests/{id}/accept`, and `PUT /requests/{id}/decline`.
- All request endpoints are authenticated and ownership-scoped per authorization matrix notes.
- [Source: docs/architecture/5-api-specification.md#51-endpoints-summary]
- [Source: docs/architecture/5-api-specification.md#56-authorization-matrix]

### File Locations

- API route/handler surfaces for request endpoints live under `internal/api/routes.go` and `internal/api/handlers/requests.go`.
- Request business logic belongs in `internal/service/request.go`.
- Request persistence lives in repository interfaces and SQLite implementation under `internal/repository/interfaces.go` and `internal/repository/sqlite/request.go`.
- Domain model path includes `internal/models/request.go`.
- Migration changes belong under `migrations/`.
- [Source: docs/architecture/source-tree.md]
- [Source: docs/architecture/10-cli-backend-architecture.md#103-api-server-architecture]

### Technical Constraints

- Preserve service-layer business logic and repository abstraction boundaries (no direct DB access from handlers/CLI).
- Apply coding standards for context propagation, wrapped errors, structured logging, DI, and no globals.
- Use normalized API error response shape and map domain errors to appropriate HTTP status behavior.
- [Source: docs/architecture/2-high-level-architecture.md#25-architectural-patterns]
