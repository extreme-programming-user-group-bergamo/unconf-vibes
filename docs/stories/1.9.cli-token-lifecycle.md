# Story 1.9: CLI Token Lifecycle & Authenticated Client

**Status:** Done

**Epic:** 1 - Foundation & Authentication

---

## Story

**As an** authenticated user,
**I want** the CLI to automatically refresh my expired access token using my stored refresh token,
**so that** I don't have to re-login unnecessarily when my access token expires during normal usage.

---

## Acceptance Criteria

1. An `AuthenticatedClient` wrapper exists in `internal/client/` that automatically attaches the stored access token to all authenticated API requests
2. When an authenticated API call returns `401` (expired/invalid token), the wrapper automatically attempts to refresh the access token by calling `POST /auth/refresh` with the stored refresh token
3. On successful refresh, both access token and refresh token are updated in the OS keychain, and the original API request is retried transparently
4. On failed refresh (invalid/expired/revoked refresh token), stored tokens are cleared from keychain and a sentinel error (`ErrSessionExpired`) is returned so commands can prompt re-login
5. `unconf status` command is refactored to use the new `AuthenticatedClient` — no manual token retrieval or passing
6. All new code has comprehensive unit tests covering happy paths, refresh success, refresh failure, and error propagation
7. Integration tests verify `POST /auth/refresh` endpoint: successful token rotation, invalid refresh token rejection, expired refresh token rejection, and revoked refresh token rejection

### API Specification — Token Refresh

[Source: docs/architecture/5-api-specification.md#54-token-lifecycle-controls]

**`POST /auth/refresh`** (unauthenticated endpoint — does NOT require Bearer token):
- Request body: `{"refresh_token": "<opaque_refresh_token>"}`
- Success response (`200 OK`):

```json
{
  "access_token": "<new_paseto>",
  "token_type": "Bearer",
  "expires_in": 86400,
  "refresh_token": "<new_opaque_refresh_token>",
  "user": {
    "id": 1,
    "github_id": "12345",
    "email": "user@example.com",
    "display_name": "octocat"
  }
}
```

- Error responses:
  - `401` with code `invalid_refresh_token` — token not found or invalid
  - `401` with code `expired_refresh_token` — token has expired (past `refresh_ttl` of 7 days)
  - `401` with code `revoked_refresh_token` — token has been revoked or already rotated

**Token Lifecycle Controls:**
- Access Token TTL: 24 hours
- Refresh Token TTL: 7 days
- Refresh rotates token: old refresh token is invalidated, new one issued
- Replay Protection: `jti` claim + denylist for revoked/rotated tokens

### Existing Backend Implementation

[Source: internal/service/auth_service.go, internal/api/handlers/auth.go]

The backend `POST /auth/refresh` is fully implemented:

- `AuthService.Refresh(ctx, refreshToken)` in `internal/service/auth_service.go`:
  - Looks up session by `auth.HashRefreshToken(refreshToken)`
  - Validates session is not revoked (`RevokedAt == nil`, `ReplacedByID == nil`)
  - Validates session is not expired (`ExpiresAt.After(now)`)
  - Fetches user, issues new session tokens via `issueSessionTokens(ctx, user, session)`
  - Returns `AuthResult` with new access + refresh token
- `AuthHandler.Refresh(c)` in `internal/api/handlers/auth.go`:
  - Binds `{"refresh_token": "..."}` from JSON body
  - Calls `authService.Refresh(ctx, refreshToken)`
  - Maps errors via `mapAuthError()` to appropriate HTTP status + error codes
- Route registration: `router.POST("/auth/refresh", authHandler.Refresh)` — UNprotected (no auth middleware)

### Existing Client Implementation

[Source: internal/client/client.go]

The HTTP client already has the `RefreshToken` method:

```go
func (c *Client) RefreshToken(ctx context.Context, refreshToken string) (*TokenResponse, error)
```

This calls `POST /auth/refresh` with `{"refresh_token": refreshToken}`. Returns `*TokenResponse` on success (same shape as device code exchange response). Error handling wraps failure with context message.

The client also has `ErrUnauthorized` sentinel error and `mapAPIErrorCode()` for error mapping.

### Current `status` Command Pattern (to be refactored)

[Source: internal/cli/status.go]

Current flow:
1. Check `RequireAuth(store)` → early exit if not logged in
2. Get access token from `tokenStore.GetAccessToken()`
3. Call `statusClient.GetMe(ctx, accessToken)` — passing token manually
4. On `client.ErrUnauthorized`: clear tokens, prompt re-login
5. On other errors: show connection error

**Problem:** Step 4 clears tokens immediately on 401 without attempting refresh. This is the primary gap.

**Refactored flow with `AuthenticatedClient`:**
1. Check `RequireAuth(store)` → early exit if not logged in (keep this for instant UX feedback)
2. Call `authClient.GetMe(ctx)` — token handled internally
3. The `AuthenticatedClient` internally: attaches token → on 401 → refreshes → retries → updates store
4. On `client.ErrSessionExpired`: prompt re-login (tokens already cleared by `AuthenticatedClient`)
5. On other errors: show connection error

### Architecture & Layering Constraints

[Source: docs/architecture/16-coding-standards.md, docs/architecture/coding-standards.md]

- **CLI → HTTP Client → REST API** — CLI NEVER accesses DB directly
- **Constructor injection:** `AuthenticatedClient` takes `*Client` + `auth.TokenStore` via constructor
- **Interface-based DI:** Define `AuthenticatedStatusClient` (or redefine `StatusClient`) interface with `GetMe(ctx) (*UserResponse, error)` — no `accessToken` parameter
- **Error wrapping:** All errors must use `fmt.Errorf("failed to X: %w", err)`
- **Logging:** Use `log/slog` for refresh attempts, token updates, failures. Never log tokens.
- **Context propagation:** All methods accept `context.Context` as first parameter
- **Configuration:** Via Viper wrapper — no `os.Getenv`. API endpoint from `cfg.GetAPIEndpoint()`.

### Error Handling

[Source: docs/architecture/17-error-handling-strategy.md, internal/service/errors.go, internal/client/client.go]

New sentinel error needed in `internal/client/client.go`:

```go
var ErrSessionExpired = errors.New("session expired: please run 'unconf login' to re-authenticate")
```

This is returned by `AuthenticatedClient` when:
1. Access token returns 401 AND
2. Refresh attempt also fails (invalid/expired/revoked refresh token) AND
3. Tokens have been cleared from keyring

Backend error codes for refresh failures (from `mapAuthError` in `auth.go`):
- `invalid_refresh_token` → 401
- `expired_refresh_token` → 401
- `revoked_refresh_token` → 401

### Wiring in `root.go`

[Source: internal/cli/root.go]

Current wiring:
```go
store := auth.NewKeyringTokenStore("unconf")
apiClient := client.NewClient(apiEndpoint)
rootCmd.AddCommand(newStatusCmd(apiClient, store))
```

New wiring:
```go
store := auth.NewKeyringTokenStore("unconf")
apiClient := client.NewClient(apiEndpoint)
authClient := client.NewAuthenticatedClient(apiClient, store)
rootCmd.AddCommand(newStatusCmd(authClient))
```

Note: `newLoginCmd` and `newLogoutCmd` continue to use `apiClient` directly — they manage the auth lifecycle explicitly and should NOT use the auto-refresh wrapper.

- Valid refresh token → 200 with rotated tokens
- Invalid refresh token → 401
- Expired refresh token → 401
- Token rotation invalidates previous refresh token → 401 on reuse
