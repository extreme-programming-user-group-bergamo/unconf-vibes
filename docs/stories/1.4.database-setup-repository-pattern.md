**Status:** Done

### Data Models – Users Table

[Source: docs/architecture/4-data-models.md#user]

```go
type User struct {
    ID             int64     `json:"id" db:"id"`
    GitHubID       string    `json:"github_id" db:"github_id"`
    Email          string    `json:"email" db:"email"`
    DisplayName    string    `json:"display_name" db:"display_name"`
    PrivacySetting string    `json:"privacy_setting" db:"privacy_setting"`
    CreatedAt      time.Time `json:"created_at" db:"created_at"`
    UpdatedAt      time.Time `json:"updated_at" db:"updated_at"`
}
```

**Key validation rules:**
- `github_id`: Must be unique and non-empty
- `email`: Must be non-empty
- `display_name`: Must be non-empty
- `privacy_setting`: Enum constraint (values: 'public', 'private')
- Timestamps: Generated server-side (UTC timezone)

### Database Schema

[Source: docs/architecture/9-database-schema.md#users-table]

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    github_id TEXT NOT NULL UNIQUE,
    email TEXT NOT NULL,
    display_name TEXT NOT NULL,
    privacy_setting TEXT NOT NULL DEFAULT 'public' CHECK (privacy_setting IN ('public', 'private')),
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_users_github_id ON users(github_id);
```

**Future tables** (defined in architecture but NOT required for this story): conferences, rooms, bookings, roommate_requests, conference_organizers, email_logs. These will be created in subsequent stories.

### Repository Pattern Design

[Source: docs/architecture/16-coding-standards.md#repository-pattern]

**Core principles:**
- All database access flows through repository interfaces (NO direct SQL in services)
- Repositories are dependency-injected via constructors (NO globals)
- Each repository implements a typed interface (e.g., `UserRepository`)
- SQLite implementation lives in `internal/repository/sqlite/`

**Interface placement:** `internal/repository/interfaces.go`  
**SQLite implementation:** `internal/repository/sqlite/user_repository.go`  

### File Locations & Directory Structure

[Source: docs/architecture/11-unified-project-structure.md]

```
internal/
├── repository/
│   ├── interfaces.go                    # Define UserRepository interface
│   └── sqlite/
│       ├── db.go                        # Connection manager & migration runner
│       └── user_repository.go           # UserRepository implementation
├── models/
│   ├── user.go                          # User domain struct (already exists from story 1.2)
```

**Database file location (at runtime):**
- Development: `.unconf.db` (in project root)
- Environment variable override: `UNCONF_DB_PATH` (if set, use this path instead)

### Error Handling

[Source: docs/architecture/17-error-handling-strategy.md]

**Domain errors to define in `internal/repository/errors.go`:**

```go
var (
    ErrUserNotFound = errors.New("user not found")
    ErrUserExists   = errors.New("user already exists")
    ErrDatabaseInit = errors.New("failed to initialize database")
)
```

**All errors from repository must be wrapped with context:**
```go
// ✓ CORRECT
return nil, fmt.Errorf("failed to fetch user by github_id: %w", err)

// ✗ WRONG
return nil, err
```

### Logging

[Source: docs/architecture/16-coding-standards.md#logging]

- Use only `log/slog` for structured logging (no fmt.Println)
- Log database initialization success/failure
- Log migration execution at INFO level
- Log connection pool status at DEBUG level

### Coding Standards & Conventions

[Source: docs/architecture/16-coding-standards.md]

- **File naming:** snake_case files (e.g., `user_repository.go`)
- **Interface naming:** PascalCase with verb (e.g., `UserRepository`)
- **Defer cleanup:** Always `defer rows.Close()` in queries
- **Context propagation:** First parameter to all I/O functions must be `context.Context`
- **No globals:** All dependencies injected via constructors
- **Viper config:** Use Viper wrapper only (never `os.Getenv` directly)

### Testing Requirements

[Source: docs/architecture/15-testing-strategy.md]

**Unit Tests (via mocking repository):**
- Mock `UserRepository` interface using a test double
- Test service layer logic that depends on database operations

**Integration Tests (in-memory SQLite):**
- Create `:memory:` SQLite database for each test
- Run migrations on test DB
- Test actual repository implementations
- Test user creation, retrieval, updates

**Example integration test pattern:**
```go
func TestUserRepository_Create(t *testing.T) {
    db := setupTestDB(t)  // in-memory :memory: DB with migrations
    defer db.Close()
    
    repo := sqlite.NewUserRepository(db)
    user, err := repo.Create(context.Background(), &User{
        GitHubID:    "test-user",
        Email:       "test@example.com",
        DisplayName: "Test User",
    })
    
    require.NoError(t, err)
    require.NotNil(t, user)
}
```

### Migration System

[Source: docs/architecture/2-high-level-architecture.md#migration-strategy]

**Tool:** golang-migrate  
**Location:** `migrations/` directory (to be created)  
**File naming:** `{version}_{description}.up.sql` and `{version}_{description}.down.sql`

**First migration (1_init.up.sql):**
- Create users table with all fields and constraints
- Create idx_users_github_id index

**First rollback (1_init.down.sql):**
- DROP TABLE users cascade

**Execution:**
- Run migrations automatically on server startup (before serving requests)
- CLI commands should also initialize DB on first run
- Make available via `make migrate-up` and `make migrate-down` targets

## Implementation Notes for Developer

### Key Reminders
1. **Repository Pattern is CRITICAL** — All DB access must go through interfaces. This enables mocking in tests and swapping to PostgreSQL later.
2. **Context propagation** — Every I/O function must accept `context.Context` as first parameter (enables request cancellation, tracing).
3. **Error wrapping** — Always wrap errors with `fmt.Errorf("context: %w", err)` to preserve stack trace.
4. **Migrations ARE the schema** — The SQL migration files in `migrations/` are the source of truth; they must match the architecture docs exactly.
5. **In-memory SQLite for tests** — Use `:memory:` databases for integration tests; they're fast and isolated.

### External Dependencies to Add
- `github.com/golang-migrate/migrate/v4` (migration runner)
- `github.com/golang-migrate/migrate/v4/database/sqlite3` (SQLite driver for migrations)

- `github.com/mattn/go-sqlite3` (SQLite3 driver)
- `github.com/stretchr/testify` (testing utilities, if not already present)
