# Story 1.8: Auth Middleware & User Profile Endpoints

**Status:** Approved

**Epic:** 1 - Foundation & Authentication

---

## Story

**As an** authenticated user,  
**I want** protected API endpoints that verify my identity and let me view/update my profile,  
**so that** the API enforces authentication and I can manage my account information.

---

## Acceptance Criteria

1. Auth middleware extracts Bearer token from `Authorization` header, validates the PASETO token via `TokenService`, extracts user identity (`sub`, `sid`) and stores it in `gin.Context`; returns `401` if token is missing, invalid, or expired
2. `POST /auth/revoke` endpoint revokes the current session/refresh token using the authenticated user's session ID from the token claims
3. `GET /users/me` endpoint returns the current authenticated user's profile (id, github_id, email, display_name, privacy_setting, created_at, updated_at)
4. `PUT /users/me` endpoint updates the current user's mutable profile fields (display_name, privacy_setting) and returns the updated profile
5. `unconf status` CLI command calls `GET /users/me` with the stored token and displays the authenticated user's profile information; shows an error if not logged in
6. All new endpoints have comprehensive unit tests for happy and unhappy paths
7. Integration tests verify auth middleware rejects unauthenticated requests and passes authenticated requests through correctly

Story 1.7 (Done) established the CLI-side auth flow. Key takeaways relevant to 1.8:

- **DI refactor pattern:** Commands use constructor-injected interfaces (`AuthClient`, `RevokeClient`), not concrete `client.Client`. Follow this pattern for `StatusClient`.

- **`RequireAuth(store TokenStore) error`** helper exists in `internal/auth/store.go` — returns `ErrNotAuthenticated` if no token in keyring. Use this in `unconf status`.
- **`MockTokenStore`** in `internal/auth/mock_store.go` — already available for tests.
- **Client error mapping:** `mapAPIErrorCode()` in `internal/client/client.go` maps backend codes to sentinel errors.
- **CLI output pattern:** Use `cmd.OutOrStdout()` and `cmd.ErrOrStderr()` for testable I/O.
- **38 tests passing** across auth, client, cli packages — do not regress.

### API Specification References

[Source: docs/architecture/5-api-specification.md#51, #53, #54, #56]

**Protected endpoints to implement:**

| Method | Path | Description | Auth |
|--------|------|-------------|------|
| POST | /auth/revoke | Revoke current token/session | Yes |
| GET | /users/me | Get current user profile | Yes |
| PUT | /users/me | Update profile (display_name, privacy_setting) | Yes |

**Token Claim Validation Policy:**

- **Required claims:** `iss`, `aud`, `sub`, `role`, `iat`, `nbf`, `exp`, `jti`
- **Issuer:** must exactly match `"unconf-api"`
- **Audience:** must contain `"unconf-cli"`
- **Time rules:** reject missing/invalid `nbf`/`exp`; enforce max clock skew ±60s
- **Token age:** reject tokens older than 24h based on `iat`
- **Failure behavior:** return `401` with normalized auth error code

**Token currently embeds:** `iss`, `aud`, `sub` (user ID as string), `sid` (session ID as string), `iat`, `nbf`, `exp`, `jti` — see `TokenService.IssueAccessToken()` in `internal/auth/token_service.go`.

Note: The architecture spec mentions a `role` claim but the current `IssueAccessToken` does not set one. The middleware should parse `role` if present but not require it for now — the role claim can be added to token issuance in a future story when organizer role checks are needed.

**Revocation flow:** `POST /auth/revoke` revokes current session immediately. CLI `unconf logout` already calls `RevokeToken()` on the client side.
