# Story 5.1: Organizer Role & Permissions

**Status:** Done

**Epic:** 5 - Organizer Tools & Hotel Automation

**Issue Type:** Story

---

## Story

**As a** developer,  
**I want** organizer role and permissions implemented,  
**so that** organizers have access to management features.

---

## Acceptance Criteria

1. `conference_organizers` junction table: conference_id, user_id, role (owner/admin)
2. Organizer middleware validates permission for protected endpoints
3. Organizers can view all attendee data regardless of privacy settings
4. Conference creators automatically become owners
5. Owners can add/remove other organizers
6. API returns 403 for non-organizers on protected endpoints

## Dev Notes

### Story Source

- Story statement and acceptance criteria sourced from Epic 5 Story 5.1.
- [Source: docs/prd/epic-5-organizer-tools-hotel-automation.md#story-51-organizer-role-permissions]

### Architecture Alignment

- Organizer authorization is designed as middleware at API route boundaries, with business rules in service layer and data access through repository interfaces.
- Organizer role semantics are `owner` and `admin`, and protected paths must enforce 403 for authenticated but unauthorized users.
- [Source: docs/architecture/10-cli-backend-architecture.md#103-api-server-architecture]
- [Source: docs/architecture/2-high-level-architecture.md#25-architectural-patterns]
- [Source: docs/architecture/5-api-specification.md#56-authorization-matrix]

### Data Models & Schema

- `ConferenceOrganizer` exists in architecture data models and is backed by `conference_organizers` schema with unique `(conference_id, user_id)` and role constraint.
- `User` privacy settings continue to exist, but organizer workflow requires scoped bypass for organizer logistics views.
- [Source: docs/architecture/4-data-models.md#47-conferenceorganizer]
- [Source: docs/architecture/9-database-schema.md#91-schema-ddl]
- [Source: docs/architecture/4-data-models.md#42-user]

### File Locations

- API routing/middleware integration: `internal/api/routes.go`, `internal/api/middleware/auth.go`, and likely `internal/api/middleware/organizer.go` (new).
- Handler layer likely additions: `internal/api/handlers/conferences.go` (conference create ownership bootstrap) and `internal/api/handlers/organizers.go` (new organizer membership endpoints).
- Service layer likely additions: `internal/service/conference_service.go` (create + owner bootstrap), `internal/service/organizer_service.go` (new).
- Repository/data layer likely additions: `internal/repository/interfaces.go`, `internal/repository/sqlite/organizer_repository.go` (new), `internal/models/conference_organizer.go` (new), migrations under `migrations/`.
- [Source: docs/architecture/source-tree.md]
- [Source: docs/architecture/10-cli-backend-architecture.md#103-api-server-architecture]

### Technical Constraints

- Keep CLI as API client only; all organizer authz/business logic remains in backend middleware/service/repository layers.
- Follow coding standards for context propagation, error wrapping, repository pattern usage, and structured logging.
- Return normalized API error envelopes for authorization failures (403).
- [Source: docs/architecture/2-high-level-architecture.md#25-architectural-patterns]
- [Source: docs/architecture/coding-standards.md#critical-rules]
- [Source: docs/architecture/17-error-handling-strategy.md#171-error-response-format]

### Project Structure Notes

- Current codebase does not yet include organizer middleware/repository/model files, so this story establishes the base RBAC substrate required by later Epic 5 stories (`create`, `rooms add/edit/remove`, `dashboard`, `export`).
- Ensure implementation order supports downstream stories by delivering stable organizer-check primitives and owner/admin role semantics first.
- [Source: docs/prd/epic-5-organizer-tools-hotel-automation.md]
