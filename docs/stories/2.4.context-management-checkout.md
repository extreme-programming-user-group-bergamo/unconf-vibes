# Story 2.4: Context Management (Checkout)

**Status:** Ready for Review

**Epic:** 2 - Conference Discovery & Context

---

## Story

**As an** attendee,
**I want** to run `unconf checkout <conference>` to set my active context,
**so that** subsequent commands operate on that conference.

---

## Acceptance Criteria

1. `unconf checkout <slug>` sets active conference context
2. Context stored in local config file (persists across sessions)
3. `unconf checkout` (no argument) shows current context
4. Success message confirms context switch: "Switched to socrates-26"
5. Error if conference slug doesn't exist
6. Context indicator available for TUI header (story dependency for Epic 3)

---

## Scope Clarifications

### AC6 — Context Indicator for TUI Header
This story provides the `ContextManager` with `GetActiveConference()` so that future TUI components (Epic 3) can read the current context. No TUI work is done in this story — only the data layer for reading context is exposed.

### Updating Existing Commands (Out of Scope)
Story 2.3 AC4 notes: "If context is set, `unconf info` (no argument) shows current context conference." That integration is **deferred** — the `info` command currently requires a slug argument (`cobra.ExactArgs(1)`). Updating `info` to fall back to the active context is a follow-up task outside this story's scope.

### Context Storage Design

[Source: docs/prd/epic-2-conference-discovery-context.md — Story 2.4 AC2]

The context is stored **locally on the CLI side** (not on the server). The chosen approach:

- **Context directory:** `~/.unconf/` (created with `0700` permissions)
- **Context file:** `~/.unconf/context` (plain text, contains only the conference slug, `0600` permissions)
- **Why plain text?** The context is a single value (slug string). No need for YAML/JSON overhead. Simple to read, write, and test.
- **Why separate from config file?** The config file (`.unconf.yaml`) is managed by Viper for read-only settings. Writing back to it via Viper would dump all defaults, polluting the file. A separate context file keeps mutable state cleanly separated from configuration.

### CLI Command Patterns

[Source: internal/cli/info.go, internal/cli/list.go, internal/cli/status.go]

- **Interface-based DI:** Each command defines local interfaces for its dependencies. The `checkout` command defines both `CheckoutClient` (for API calls) and `CheckoutContextStore` (for context read/write).
- **Constructor pattern:** `newXxxCmd(deps...) *cobra.Command` → `RunE` dispatches to `runXxx(cmd, deps, args...)`.
- **Output:** Use `cmd.OutOrStdout()` for normal output, `cmd.ErrOrStderr()` for error messages.
- **Error handling:** User-friendly messages to stderr, wrapped `fmt.Errorf` returned.
- **Test pattern:** Mock structs with function fields, individual test functions, `bytes.Buffer` for stdout/stderr capture.
