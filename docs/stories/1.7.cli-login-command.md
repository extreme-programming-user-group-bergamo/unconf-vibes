# Story 1.7: CLI Login Command

**Status:** Done

**Epic:** 1 - Foundation & Authentication

---

## Story

**As an** attendee,  
**I want** to run `unconf login` to authenticate with my GitHub account,  
**so that** I can access UNCONF features.

---

## Acceptance Criteria

1. `unconf login` command initiates GitHub device flow
2. User shown device code and URL to enter it (https://github.com/login/device)
3. CLI polls backend for authentication completion
4. On success, auth token stored securely in OS keychain
5. Success message displayed with user's GitHub username
6. Subsequent commands can detect authenticated state
7. `unconf logout` command removes stored credentials

---

## Dev Notes

### Project Context

This story implements the CLI-side login experience, consuming the backend auth endpoints established in Story 1.6. It introduces the HTTP client layer, OS keychain token storage, and the `unconf login` / `unconf logout` Cobra commands.

**Previous Story Context:** Story 1.6 (Done) implemented backend auth endpoints: `POST /auth/device`, `POST /auth/token`, `POST /auth/refresh`. The backend has `AuthService` in `internal/service/auth_service.go`, `GitHubProvider` in `internal/auth/github_provider.go`, and `TokenService` in `internal/auth/token_service.go`. This story is **CLI-side only** — no backend modifications required.

### Product & Requirement References

[Source: docs/prd/epic-1-foundation-authentication.md, docs/prd/requirements.md]

- Epic 1 Story 1.7 defines CLI login as the end-to-end authentication command, proving the full stack works.
- FR1 requires GitHub OAuth device flow for CLI authentication.
- CLI NEVER accesses DB directly — all auth interaction goes through HTTP client → REST API.

### API Contract (Backend Endpoints Consumed)

[Source: docs/architecture/5-api-specification.md#52-authentication-flow]

The CLI consumes these existing backend endpoints:

- `POST /auth/device` (unauthenticated): Initiates device flow. Returns:

```json
{
  "device_code": "...",
  "user_code": "ABCD-1234",
  "verification_uri": "https://github.com/login/device",
  "expires_in": 900,
  "interval": 5
}
```

- `POST /auth/token` (unauthenticated): Polls for token exchange. Request body: `{"device_code": "..."}`. Returns:
  - `202 Accepted` with `{"status": "authorization_pending", "interval": 5}` while pending.
  - `200 OK` on success:

```json
{
  "access_token": "<paseto>",
  "token_type": "Bearer",
  "expires_in": 86400,
  "refresh_token": "<opaque>",
  "user": {
    "id": 1,
    "github_id": "12345",
    "email": "user@example.com",
    "display_name": "octocat"
  }
}
```

  - `400` for invalid device code, `401` for denied/expired.

- `POST /auth/refresh` (authenticated): Token rotation. Request body: `{"refresh_token": "..."}`. Returns rotated `AuthResult` payload on success.

- `POST /auth/revoke` (authenticated): Revokes current token/session. Called by `unconf logout` when online.

### HTTP Client Layer

[Source: docs/architecture/source-tree.md — `internal/client/`]

Create `internal/client/client.go` as the base HTTP client for all CLI-to-API communication:

- Use `go-resty/resty/v2` as the HTTP client library (approved in tech stack).
- Base URL from `cfg.GetAPIEndpoint()` (default: `http://localhost:8080`).
- Auth header injection: set `Authorization: Bearer <access_token>` on authenticated requests.
- JSON content type by default.
- Accept `context.Context` on all request methods.
- Constructor: `NewClient(baseURL string) *Client` (or with functional options).
- Auth methods needed for this story:
  - `StartDeviceFlow(ctx) (*DeviceFlowResponse, error)` → `POST /auth/device`
  - `ExchangeDeviceCode(ctx, deviceCode) (*TokenResponse, error)` → `POST /auth/token`
  - `RefreshToken(ctx, refreshToken) (*TokenResponse, error)` → `POST /auth/refresh`
  - `RevokeToken(ctx, accessToken) error` → `POST /auth/revoke`
- Define response structs for client-side deserialization (mirroring backend `AuthResult` shape).
- Handle HTTP error responses: map status codes to meaningful client-side errors.
- No `internal/client/` directory exists yet — it must be created.
- No `resty` dependency in `go.mod` yet — must be added via `go get`.

### Token Storage (Keyring)

[Source: docs/architecture/source-tree.md — `internal/auth/store.go`, docs/architecture/tech-stack.md]

Create `internal/auth/store.go` for OS keychain token storage:

- Use `zalando/go-keyring` (approved in tech stack, v0.2.6+).
- Service name: `"unconf"`.
- Store both access token and refresh token as separate keyring entries (e.g., keys: `"access_token"`, `"refresh_token"`).
- Define interface `TokenStore` with methods:
  - `SaveTokens(accessToken, refreshToken string) error`
  - `GetAccessToken() (string, error)`
  - `GetRefreshToken() (string, error)`
  - `ClearTokens() error`
  - `HasValidToken() bool` — checks if an access token exists in keyring.
- Implement `KeyringTokenStore` struct satisfying the interface.
- Constructor injection: `NewKeyringTokenStore(serviceName string) *KeyringTokenStore`.
- No `go-keyring` dependency in `go.mod` yet — must be added via `go get`.
- Wrap all keyring errors with context.

### Login Command

[Source: docs/architecture/source-tree.md — `internal/cli/login.go`, docs/architecture/8-core-workflows.md#81-user-login-flow]

Create `internal/cli/login.go` implementing `unconf login`:

1. Create Cobra command via `newLoginCmd(...)` factory (matches existing pattern in `root.go`).
2. Register with `rootCmd.AddCommand(newLoginCmd(...))` in `NewRootCmd()`.
3. Command flow:
   - Call `POST /auth/device` via HTTP client to get device code.
   - Display device code and verification URL to user via `fmt.Fprintf(cmd.OutOrStdout(), ...)`.
   - Poll `POST /auth/token` with the `device_code` every `interval` seconds (from device flow response).
   - On `202 Accepted` (pending): continue polling.
   - On `200 OK` (success): store access token and refresh token via `TokenStore.SaveTokens(...)`.
   - Display welcome message: `"Welcome, <display_name>! You are now logged in."`.
4. Error handling:
   - Expired device code → prompt user to retry.
   - Access denied → inform user authorization was denied.
   - Network errors → display connection error with API endpoint.
   - Already logged in → check `TokenStore.HasValidToken()` and inform user (allow `--force` flag to re-login).
5. Polling implementation:
   - Use `time.NewTicker` with interval from device flow response.
   - Respect `context.Context` cancellation (Ctrl+C graceful exit).
   - Set max poll duration based on `expires_in` from device flow response.

### Logout Command

[Source: docs/architecture/source-tree.md — `internal/cli/logout.go`, docs/architecture/5-api-specification.md#54-token-lifecycle-controls]

Create `internal/cli/logout.go` implementing `unconf logout`:

1. Create Cobra command via `newLogoutCmd(...)` factory.
2. Register with `rootCmd.AddCommand(newLogoutCmd(...))` in `NewRootCmd()`.
3. Command flow:
   - Retrieve access token from `TokenStore.GetAccessToken()`.
   - If token exists, attempt to call `POST /auth/revoke` via HTTP client (best-effort; don't fail if offline).
   - Clear all stored credentials via `TokenStore.ClearTokens()`.
   - Display confirmation: `"You have been logged out."`.
4. If no credentials stored, display: `"You are not currently logged in."`.

### Auth State Detection Helper

Create a helper function (e.g., in `internal/auth/store.go` or `internal/cli/auth_helper.go`) that:

- Checks `TokenStore.HasValidToken()` for existence of an access token.
- Can be called by other commands to gate authenticated-only operations.
- Returns a clear error message when not authenticated, guiding user to run `unconf login`.

[Source: docs/architecture/17-error-handling-strategy.md]

- Map backend error responses to user-friendly CLI messages.
