# Story 1.6: GitHub OAuth Integration (Backend)

**Status:** Approved

**Epic:** 1 - Foundation & Authentication

---

## Story

**As a** backend developer,  
**I want** GitHub OAuth device flow endpoints implemented,  
**so that** CLI users can authenticate without browser redirects.

---

## Acceptance Criteria

1. `POST /auth/device` endpoint initiates device flow, returns `device_code` and `user_code`
2. `POST /auth/token` endpoint polls for access token completion
3. GitHub OAuth app credentials configurable via environment variables
4. On successful auth, user record created/updated in database
5. PASETO token issued for subsequent API authentication
6. Token expiry and refresh mechanism defined

---

## Dev Notes

### Project Context

This story introduces backend authentication for CLI login via GitHub Device Flow and establishes token lifecycle behavior for authenticated API usage.

**Previous Story Context:** Story 1.5 established CI/CD quality gates. This story adds auth endpoints and service/repository wiring that Story 1.7 (`unconf login`) will consume.

### Product & Requirement References

[Source: docs/prd/epic-1-foundation-authentication.md, docs/prd/requirements.md]

- Epic 1 Story 1.6 defines backend GitHub OAuth device flow as prerequisite for CLI login.
- FR1 requires GitHub OAuth device flow for CLI authentication.
- NFR9/NFR10 require secure transport and secure token handling assumptions.

### API Contract

[Source: docs/architecture/5-api-specification.md#52-authentication-flow]

Required auth endpoints for this story scope:

- `POST /auth/device` (unauthenticated): request GitHub device code and return normalized payload to CLI.
- `POST /auth/token` (unauthenticated): poll GitHub token endpoint using device code; return:
  - `202 Accepted` while authorization is pending.
  - `200 OK` with API token and user payload after successful authorization.
- `POST /auth/refresh` (authenticated): token rotation endpoint must be defined and implemented at least as baseline lifecycle support for AC6.

Suggested response payload alignment:

```json
{
  "device_code": "...",
  "user_code": "...",
  "verification_uri": "https://github.com/login/device",
  "expires_in": 900,
  "interval": 5
}
```

```json
{
  "access_token": "<paseto>",
  "token_type": "Bearer",
  "expires_in": 86400,
  "refresh_token": "<opaque-or-jti-bound-refresh>",
  "user": {
    "id": 1,
    "github_id": "12345",
    "email": "user@example.com",
    "display_name": "octocat"
  }
}
```

### Architecture & Layering Constraints

[Source: docs/architecture/6-components.md, docs/architecture/10-cli-backend-architecture.md, docs/architecture/16-coding-standards.md]

- Handler layer in `internal/api/handlers/auth.go` validates request/response and delegates to service layer.
- Service layer encapsulates OAuth exchange, user upsert, and token issuance.
- Repository layer owns DB persistence; no SQL in services.
- All I/O functions must accept `context.Context` first.
- Use constructor injection for GitHub OAuth client, token service, and repositories.
- Configuration must flow via existing config wrapper (Viper-based), not direct `os.Getenv` in handlers/services.

### Security, Token, and Session Notes

[Source: docs/architecture/14-security-and-performance.md, docs/architecture/5-api-specification.md#54-token-lifecycle-controls]

- PASETO profile: `v4.local`.
- Access token TTL target: 24 hours.
- Claims policy should include at minimum: `iss`, `aud`, `sub`, `iat`, `nbf`, `exp`, `jti`.
- Add/define refresh behavior with `POST /auth/refresh` token rotation and invalidation of prior token/session chain.
- Add token replay protections using `jti` denylist/session tracking structure (minimum viable server-side mechanism can be in-memory for now, but interface must support persistence evolution).
- Apply rate-limiting/backoff considerations for `/auth/token` polling to avoid abuse.

### GitHub OAuth Device Flow Notes

[Source: docs/architecture/8-core-workflows.md#81-user-login-flow, docs/prd/technical-assumptions.md]

- Backend initiates device flow against GitHub `/login/device/code`.
- Backend polls/exchanges device code against GitHub `/login/oauth/access_token`.
- Handle GitHub pending/error states (`authorization_pending`, `slow_down`, `expired_token`, `access_denied`) and map them to normalized API responses.
- After GitHub token success, fetch GitHub user identity and email as needed to create/update local user.

### Data Model & Persistence Notes

[Source: docs/architecture/4-data-models.md#42-user, docs/architecture/9-database-schema.md#users-table]

- `users` table already exists from Story 1.4 with unique `github_id`.
- Upsert behavior should:
  - Create user when `github_id` not present.
  - Update `email`, `display_name`, `updated_at` when `github_id` exists.
- Ensure repository contract exposes required methods (`GetByGitHubID`, `Create`, `Update`) and wraps errors with context.

### Configuration Notes

[Source: docs/architecture/6-components.md#config-manager, docs/architecture/16-coding-standards.md]

Add/confirm configuration keys (via existing config package):

- `UNCONF_GITHUB_CLIENT_ID`
- `UNCONF_GITHUB_CLIENT_SECRET`
- `UNCONF_PASETO_SYMMETRIC_KEY`
- `UNCONF_TOKEN_TTL` (default 24h)
- `UNCONF_REFRESH_TTL` (define default policy)

If config already supports env binding, wire these keys there; do not read env directly in business logic.

### Error Handling & Response Semantics

[Source: docs/architecture/17-error-handling-strategy.md]

- Define/auth domain errors in `internal/service/errors.go` and map to normalized API error responses.
- Wrap external/GitHub/DB failures with context.
- Response expectations:
  - `POST /auth/device`: `200` on success, `500` on provider/config errors.
  - `POST /auth/token`: `202` pending, `200` success, `400/401` for invalid/denied device flow, `500` internal/provider failure.
  - `POST /auth/refresh`: `200` rotated, `401` invalid/expired refresh context.

## Testing

### Relevant Testing Standards

[Source: docs/architecture/15-testing-strategy.md, docs/architecture/16-coding-standards.md]

**Test File Location:** `*_test.go` in same package as implementation  
**Test Command:** `go test ./...`  
**Framework:** `go test` + `testify`

### Required Test Coverage for Story 1.6

- **Unit Tests (Service Layer):**
  - Device flow start success + provider failure mapping.
  - Polling pending/slow_down/denied/expired/success transitions.
  - User create/update branching and repository error wrapping.
  - PASETO issuance claim completeness and TTL checks.
  - Refresh rotation invalidates prior token chain.

- **Handler/API Tests (HTTP):**
  - `POST /auth/device` success and error responses.
  - `POST /auth/token` returns `202` pending and `200` on success.
  - `POST /auth/refresh` returns rotated token on valid auth context.
  - Response body and status code contract verification.

- **Integration Tests:**
  - End-to-end path: device start -> token poll success -> user persisted -> token returned.
  - Existing user re-login updates user profile fields.
  - Invalid device code and expired flow handling.

- **Security/Behavioral Tests:**
  - Token expiry enforcement (`exp`/`iat`/clock skew checks).
  - Replay/rotation behavior after refresh (old token rejected).
  - Ensure logs do not leak OAuth or API tokens.
