# Story 1.5: CI/CD Pipeline

**Status:** Ready for Review

**Epic:** 1 - Foundation & Authentication

---

## Story

**As a** developer,  
**I want** GitHub Actions CI pipeline configured,  
**so that** code quality is enforced on every PR.

---

## Acceptance Criteria

1. GitHub Actions workflow triggers on PR and push to main
2. Pipeline runs `go test ./...` for all tests
3. Pipeline runs `golangci-lint` for static analysis
4. Pipeline fails if tests fail or linting errors exist
5. GoReleaser configuration file present (for future releases)
6. Build succeeds for linux/amd64, darwin/amd64, darwin/arm64, windows/amd64

## Dev Notes

### Project Context

This story establishes the foundation for continuous integration and delivery. The CI/CD pipeline ensures code quality gates before PRs merge and paves the way for automated releases and deployments.

**Previous Story Context:** Story 1.4 established the database and repository pattern. The CI pipeline will enforce that all code follows these architectural patterns through linting and testing.

### Technology Stack

[Source: docs/architecture/3-tech-stack.md#ci-cd]

- **CI/CD:** GitHub Actions (native GitHub integration)
- **Linting:** golangci-lint v2.x (pin latest stable) - multi-linter aggregator
- **Testing:** go test + testify v1.11+ - standard + assertions/mocks
- **Release:** GoReleaser v1.24+ - cross-platform builds and releases
- **Build Tool:** Make - universal task runner
- **Containerization:** Docker 24+ (for backend deployment)
- **Release Targets:** linux/amd64, darwin/amd64, darwin/arm64, windows/amd64

### Deployment Architecture - Build & Release Pipeline

[Source: docs/architecture/13-deployment-architecture.md#ci-cd-pipeline]

The CI/CD pipeline has three stages:

1. **CI Workflow (ci.yaml)** - Runs on every PR and push to main
   - Triggers: pull_request, push to main
   - Jobs: test, lint, build
   - Fails if any job fails

2. **Release Workflow (release.yaml)** - Triggered by version tags
   - Triggers: tags matching v\*
   - Uses GoReleaser for cross-platform builds
   - Publishes GitHub Release with binaries

3. **Deploy Workflow (deploy.yaml)** - Triggered by version tags
   - Deploys server to Fly.io (requires Fly.io credentials in secrets)
   - Skipped in this story (placeholder only)

### Testing Standards

[Source: docs/architecture/15-testing-strategy.md]

- **Test Framework:** go test (stdlib) + testify for assertions
- **Test Location:** `*_test.go` files in same package as code
- **Execution:** CI pipeline runs `go test ./...` which discovers and runs all tests
- **Coverage:** Not enforced in Story 1.5 but should show aggregate coverage for future enhancement
- **Test Types:** Unit (60%), Integration (30%), E2E Manual (10%)

### Linting Standards

[Source: docs/architecture/coding-standards.md]

CI pipeline enforces these coding standards:

- Repository Pattern - all DB access via interfaces
- Error Wrapping - errors wrapped with context using `fmt.Errorf`
- Context Propagation - context.Context as first parameter to I/O functions
- Logging - log/slog only, no fmt.Println
- Configuration - Config wrapper, no os.Getenv
- No Globals - DI instead of singletons
- Naming Conventions - files snake_case, packages lowercase, interfaces PascalCase+verb

### Workflow Files - Detailed Specifications

#### CI Workflow (ci.yaml)

- **Trigger:** pull_request (any branch), push to main
- **Runner:** ubuntu-latest
- **Steps:**
  1. Checkout code
  2. Setup Go 1.24+
  3. Download dependencies: `go mod download`
  4. Cache Go modules for faster builds
  5. Run linting: `golangci-lint run ./...` (use config: `.golangci-lint.yaml` from project or default)
  6. Run tests: `go test ./...` with `-v` for verbose output
  7. Build CLI: `make build` (verifies build succeeds)
  8. Upload test results (optional, for GitHub UI visibility)

Configuration Notes:
- Use setup-go Action (actions/setup-go@v4)
- Use golangci-lint Action (golangci/golangci-lint-action@v4)
- Timeout: 15 minutes total (linting typically 1-2 min, tests 3-5 min)
- Cache key should include go.sum for accuracy

#### GoReleaser Configuration (.goreleaser.yaml)

[Source: docs/architecture/3-tech-stack.md#release-goreleaser-v1-24]

- **Version:** v1.24+
- **Binaries to Build:**
  - CLI: `unconf` (cmd/unconf/main.go)
  - Server: `unconf-server` (cmd/server/main.go)
- **Architectures:** linux/amd64, darwin/amd64, darwin/arm64, windows/amd64
- **Archive Format:** tar.gz for linux/darwin, zip for windows
- **Checksums:** Include sha256 checksums
- **GitHub Release:** Auto-create release with built artifacts

Example structure (do NOT invent beyond this):
```yaml
project_name: unconf
builds:
  - id: unconf
    main: ./cmd/unconf
    binary: unconf
    goos: [linux, darwin, windows]
    goarch: [amd64, arm64]
    # ... other settings
  - id: unconf-server
    main: ./cmd/server
    binary: unconf-server
    # ... similar
archives:
  - format: tar.gz
    format_overrides:
      - goos: windows
        format: zip
checksums:
  name_template: "{{ .ProjectName }}_{{ .Version }}_checksums.txt"
release:
  auto: true
```

### Makefile Targets

[Source: docs/architecture/source-tree.md]

Ensure Makefile has these targets (may already exist from earlier stories):

- `make build` - Build both CLI and server binaries (success required for CI)
- `make test` - Run `go test ./...`
- `make lint` - Run `golangci-lint run ./...`
- `make clean` - Remove bin/ directory

### File Locations & Naming

All workflow files go in `.github/workflows/` directory:

- `.github/workflows/ci.yaml`
- `.github/workflows/release.yaml`
- `.github/workflows/deploy.yaml`
- `./.goreleaser.yaml` (in project root)
- `./.golangci-lint.yaml` (in project root, or use defaults)

### Assumptions & Edge Cases

- **Go Version:** Assume Go 1.24+ is standard. If tests fail due to version drift, update setup-go step.
- **Secrets:** GitHub Actions secrets (like FLY_API_TOKEN for deploy.yaml) will be added in later stories.
- **Build Order:** CLI builds before server (no dependency between them in this story).
- **Test Failures:** Any test failure fails entire pipeline - expected behavior.
- **Linting:** All linting errors fail the pipeline - no warnings allowed.

### Integration Points

- Workflows triggered by GitHub events (PR, push, tags)
- Results visible in GitHub interface (status checks, PR requirements)
- Artifacts uploaded to GitHub Release (via GoReleaser) for download by users
- Makefile targets invoked by workflows (build, test, lint)
