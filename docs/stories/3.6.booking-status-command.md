# Story 3.6: Booking Status Command

**Status:** In Progress

**Epic:** 3 - Room Exploration & Booking

**Issue Type:** Story

---

## Story

**As an** attendee,  
**I want** to run `unconf status` to see my current booking,  
**so that** I can verify my reservation details.

---

## Acceptance Criteria

1. `unconf status` shows current booking for active conference
2. Displays: room number, type, price, check-in/out dates, privacy setting
3. Shows roommates (if any) respecting their privacy settings
4. Shows pending roommate requests (incoming/outgoing) — placeholder for Epic 4
5. "No booking" message if not booked
6. `--all` flag shows bookings across all conferences

### Data Models

- Booking model fields relevant to status display include booking `status`, `privacy_setting`, and conference/room linkage.
- Conference model includes `start_date` and `end_date`, which are the source for check-in/out date presentation in status output.
- Room model includes `room_number`, `room_type`, and `price_per_night` needed for booking detail display.
- Roommate request model defines pending request entities for incoming/outgoing placeholder display.
- [Source: docs/architecture/4-data-models.md#45-booking]
- [Source: docs/architecture/4-data-models.md#43-conference]
- [Source: docs/architecture/4-data-models.md#44-room]
- [Source: docs/architecture/4-data-models.md#46-roommaterequest]

### API Specifications

- `GET /bookings` is the primary authenticated endpoint for user booking retrieval.
- `GET /requests` is available for roommate request retrieval and supports placeholder pending-request section in this story.
- Authorization rules require user-scoped ownership handling for booking/request data.
- [Source: docs/architecture/5-api-specification.md#51-endpoints-summary]
- [Source: docs/architecture/5-api-specification.md#56-authorization-matrix]

### File Locations

- CLI command implementation: `internal/cli/status.go` and root command wiring in `internal/cli/root.go`
- Booking and request API client paths: `internal/client/bookings.go`, `internal/client/requests.go`
- Shared domain output structures as needed in `internal/models/`
- [Source: docs/architecture/source-tree.md]
- [Source: docs/architecture/10-cli-backend-architecture.md#101-cli-command-organization]

### Technical Constraints

- Enforce architecture boundary: CLI consumes API clients only; no direct service/repository/database usage in CLI command code.
- Follow critical coding rules: context propagation, error wrapping with `%w`, structured logging, config wrapper access, and no globals.
- [Source: docs/architecture/2-high-level-architecture.md]
- [Source: docs/architecture/coding-standards.md#critical-rules]

### Project Structure Notes

- No structural conflict identified. Story scope stays within existing `internal/cli` and `internal/client` modules.
- If additional status-specific render helpers are needed, keep them under `internal/cli` command-local patterns rather than introducing new top-level packages.
