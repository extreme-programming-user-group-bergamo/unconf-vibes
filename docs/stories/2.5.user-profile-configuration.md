# Story 2.5: User Profile Configuration

**Status:** Ready for Review

**Epic:** 2 - Conference Discovery & Context

---

## Story

**As an** attendee,
**I want** to run `unconf config` to set my display name and privacy preferences,
**so that** my profile is ready for booking.

---

## Acceptance Criteria

1. `unconf config` opens interactive prompts for profile setup
2. Collects: display name, email (pre-filled from GitHub), privacy preference
3. Privacy options: Public (name visible) or Private (anonymous)
4. `unconf config --show` displays current profile settings
5. Profile data sent to backend and stored in user record
6. Can update individual fields: `unconf config --privacy private`

---

## Scope Clarifications

### AC1 — Interactive Mode Testing
Interactive mode uses `bufio.Scanner` to read stdin prompts. This is inherently difficult to unit test with Cobra's test harness. Interactive mode should be verified via **manual testing** against a running server. Unit tests cover flag-based modes (`--show`, `--display-name`, `--privacy`) which exercise the same underlying client calls.

### AC2 — Email Pre-Fill (Display Only)
The interactive prompt pre-fills the email by fetching the current profile via `GetMe`. Email is **displayed as context** but is NOT editable via the config command — email comes from GitHub OAuth and is immutable in the users table. The config command only updates `display_name` and `privacy_setting`.

### AC3 — Privacy Options vs. Database
The service layer (`internal/service/user_service.go`) validates against three privacy settings: `"public"`, `"private"`, `"connections_only"`. However, the database migration (`migrations/1_init.up.sql`) has a CHECK constraint that only allows `"public"` and `"private"`. The CLI should only present `"public"` and `"private"` as options to match the database constraint. **This discrepancy is noted but NOT fixed in this story** — it is out of scope.

### AC5 — Backend Already Exists
The backend API (`PUT /users/me`), service layer (`UpdateProfile`), and repository (`Update`) are **already fully implemented and tested**. This story only adds the HTTP client method (`UpdateMe`) and the CLI command (`config`). No backend changes needed.

### Integration Test Scope
Integration tests for `PUT /users/me` are added in `cmd/server/main_integration_test.go` to validate the full round-trip (update + verify via GET). The route-level integration tests in `internal/api/routes_test.go` already cover the handler/service path for user endpoints.

### Previous Story Context (Story 2.4)

[Source: docs/stories/2.4.context-management-checkout.md — Dev Agent Record]

Story 2.4 (Done) implemented `unconf checkout` with the ContextManager pattern. Key takeaways for 2.5:

- **CLI pattern validated:** Interface-based DI → `newXxxCmd(deps)` → `RunE` dispatches to `runXxx(cmd, deps, ...)`. The `config` command follows the same pattern with `ConfigClient` interface.
- **Auth client pattern:** `AuthenticatedClient` wraps base `Client` calls with auto-refresh on 401. The `config` command needs `authClient` (like `status` command), not `apiClient`.
- **Root wiring:** Commands using auth go through `authClient` (e.g., `newStatusCmd(authClient)`). Commands using public endpoints go through `apiClient` (e.g., `newListCmd(apiClient)`).
- **Error messaging pattern:** On auth failure, print user-friendly message to `stderr`, then return wrapped error.
- **Test patterns:** Mock structs with function fields, individual test functions, `bytes.Buffer` for stdout/stderr capture, `cmd.SetArgs()`.
- **Lint note:** Use `_, _ =` pattern for `fmt.Fprintf`/`fmt.Fprintln` to satisfy errcheck linter (see info.go, checkout.go).

### Existing Backend Stack (Complete — No Changes Needed)

[Source: internal/api/handlers/users.go, internal/service/user_service.go, internal/repository/sqlite/user_repository.go]

The full backend for user profile management is already implemented:

- **API Handler** (`internal/api/handlers/users.go`):
  - `GET /users/me` → `UserHandler.GetMe` — returns authenticated user profile
  - `PUT /users/me` → `UserHandler.UpdateMe` — accepts `{"display_name": "...", "privacy_setting": "..."}` (both optional)
  - Both routes require Bearer auth via `middleware.AuthMiddleware`
  - Request binding: `UpdateProfileRequest{DisplayName *string, PrivacySetting *string}`

- **Service** (`internal/service/user_service.go`):
  - `GetProfile(ctx, userID)` → returns `*models.User`
  - `UpdateProfile(ctx, userID, UpdateProfileInput)` → validates privacy setting, updates user, returns `*models.User`
  - Privacy validation: `validPrivacySettings` map includes `"public"`, `"private"`, `"connections_only"`

- **Repository** (`internal/repository/sqlite/user_repository.go`):
  - `GetByID`, `GetByGitHubID`, `Create`, `Update` — all implemented

- **Model** (`internal/models/user.go`):
  - `User{ID, GitHubID, Email, DisplayName, PrivacySetting, CreatedAt, UpdatedAt}` with json/db tags

### Privacy Setting Discrepancy

[Source: internal/service/user_service.go line 13, migrations/1_init.up.sql line 6]

- **Service layer** validates: `"public"`, `"private"`, `"connections_only"`
- **Database CHECK constraint** allows: `"public"`, `"private"` ONLY
- **Impact:** If service allows `"connections_only"`, the DB INSERT/UPDATE will fail with a constraint error
- **For this story:** CLI should only present `"public"` and `"private"` as valid options
- **Fix:** Out of scope — should be addressed in a separate story to align service validation with DB constraint

### Integration Test Pattern

[Source: cmd/server/main_integration_test.go]

The integration test file uses a full server binary startup:
- Build server binary with `go build`
- Start with env vars: `UNCONF_API_ENDPOINT`, `UNCONF_DB_PATH`, `UNCONF_LOG_LEVEL`, `UNCONF_PASETO_SYMMETRIC_KEY`, etc.
- Wait for `/health` endpoint
- Execute HTTP calls against the running server
- Clean up with `t.Cleanup`

For `PUT /users/me` tests:
- Need a test user in the database — insert directly via SQL after server starts
- Need a valid PASETO token — generate using `auth.NewTokenService` with the same symmetric key
- Alternatively, use the device flow to create a real user (but this requires GitHub OAuth mock — more complex)
- **Simplest approach:** Insert user directly into SQLite DB, then generate a PASETO token for that user's ID
